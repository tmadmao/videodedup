# 任务 1：忽略黑/白像素的掩码比对

## 1.1 背景与要解决的问题

当前遇到带水印的视频时，实测平均汉明距离 **9.2**，超过了当时 6.4 的判定线，导致**漏检**。当时的处理办法是把全局相似度阈值从 0.90 **放宽到 0.80**。

这是一个"用精确率换召回率"的妥协：放宽阈值会让**所有**不相关的视频对更容易被判成同一组，而不只是水印那一种情况。

VDF 的做法不是放宽阈值，而是**把干扰像素排除在计分之外**：只对「两个文件在该位置都不是近黑、也不是近白」的像素计算差异。水印通常是白字（或白字带半透明黑底）、黑边/白边、烧制字幕，这些区域被直接跳过，画面主体仍然严格比对。

**这一项是本清单里收益最大的一项。** 做完之后，阈值可以往回收紧，精确率与召回率同时改善。

## 1.2 关键实现细节（易踩坑）

```
常量：黑像素 ≤ 0x20 (32)、白像素 ≥ 0xF0 (240)

对每个像素位置：
    若 ignore_black 且 (a ≤ 32 或 b ≤ 32)        → 排除
    若 ignore_white 且 (a ≥ 240 或 b ≥ 240)      → 排除
    否则计入：diff += |a - b|，count += 1

相似度 = diff / count / 255
```

三个**必须注意**的点：

1. **分母是「有效像素数 count」，不是总像素数 1024。**
   如果除以总像素数，掩掉大量水印像素后差值会被稀释、相似度虚高，掩码就白做了。这是最容易写错的地方。
2. **两个文件都要判黑/白**（`a` 或 `b` 任一为黑就排除）。因为水印可能只存在于其中一个文件；只判一边会漏掉"原片干净、副本带水印"的像素。
3. **有效像素不足时要跳过该位置**。若某帧几乎全黑（片头渐变、暗场景），有效像素极少，这个位置的比对结果没有统计意义，应**不计入该位置的投票**，而不是拿一个高噪声的值去参与判定。建议阈值：`count < 256`（即有效像素不足 25%）时跳过。

## 1.3 与现有算法如何共存：OR 门

**不要替换现有的 12 帧 pHash**，而是新增一路并行通道，判重时取「任一通道通过即算重复」：

```
指纹（同一次解码同时产出，几乎零额外抽帧成本）：
  ① 12 帧 64 位 pHash          ← 现有，保留（抗调色/亮度变化）
  ② 12 帧 32×32 灰度字节数组   ← 新增（抗水印/黑边，且像素级精确）

判定：
  dup = (pHash 通道通过) or (灰度掩码通道通过)
```

理由：两条通道的失效场景不同——pHash 对"整体调色/亮度偏移"鲁棒但对大面积规律性干扰（水印）敏感；灰度掩码正好相反。任一命中即判重，能把漏检压到最低。

**成本**：32×32 灰度是在已解码的帧上做一次 `cvtColor` + `resize`，每帧约几十毫秒（见任务 5 的实测），不需要重新解码视频。

## 1.4 改动清单

| 位置 | 改动 |
|---|---|
| `compute_features()` | 每个采样帧额外生成 32×32 灰度（`cv2.cvtColor` + `cv2.resize(…, INTER_CUBIC)`），存入 `res["gray"]` |
| `VideoItem` 数据类 | 新增 `gray: list = field(default_factory=list)` |
| 缓存 | 新增 `gray` 字段；**缓存键版本从 `v2` 升到 `v3`**（结构变更，旧缓存自动失效） |
| 新增函数 | `masked_gray_distance(a_list, b_list, ignore_black, ignore_white)` → 返回 0~1 的差异率 |
| `group_videos()` | 判定改为 OR 门；两个通道各自有独立阈值 |
| GUI 设置区 | 新增「忽略黑边像素」「忽略白边像素」两个复选框（**默认勾选**）、灰度通道阈值 |
| `--selftest` | 新增掩码有效性断言（见验收标准） |

## 1.5 验收标准

1. **掩码确实生效**：对一个带水印的样本，`masked_gray_distance(掩码关闭)` 必须**大于** `masked_gray_distance(掩码开启)`，且差值 > 0。这条断言写进 `--selftest`。
2. **水印样本回到安全区**：原有测试样本（原始 / 复制改名 / 二次转码 / 轻微裁切 / 加水印 / 完全无关）重跑，加水印那个必须与原有 4 个同源样本判为同一组。
3. **异源不受影响**：完全无关的视频的**灰度通道距离不得下降**（若下降说明掩码把有效信息也掩掉了，要复查有效像素下限）。
4. **阈值可收紧**：在满足 1~3 的前提下，把默认 pHash 阈值从 0.80 收紧回 0.85 以上而不丢检。
5. **回归**：`--selftest` 与现有 GUI 全流程测试全部通过；旧缓存自动失效重建（首次扫描变慢属预期）。

## 1.6 风险

- 若掩码比例过高（例如视频本身是大面积纯白背景），有效像素可能不足 → 靠 1.2 的第 3 点兜底（跳过该位置）。
- 阈值需要**用真实样本重新标定**，不能照搬 VDF 的 92%（它的度量是 32×32 上的平均逐像素差，与我们的汉明距离不同量纲）。

# 任务 2：质量排序器（逐级淘汰 + 近似平局容差）

## 2.1 背景与要解决的问题

当前"建议保留"的实现是**固定三元组排序**：

```python
def _group_quality_key(self, path: str):
    return ((v.width or 0) * (v.height or 0), v.bitrate or 0, v.size or 0)
```

存在三个问题：

1. **缺少「时长」判据**。一个被剪短的片段（1080p、码率高）可能压过完整的原片，用户按建议删掉就丢了完整版。
2. **没有近似平局容差**。`1920×1080 = 2,073,600` 与 `1280×720 = 921,600` 之间永远后者输——哪怕前者是 200 kbps 的糊片、后者是 8 Mbps 的高清。分辨率只差一点点的两个文件，也会被单一判据粗暴决定。
3. **缺少「每像素位数」**。`bitrate / (width × height × fps)` 是衡量画面实际信息密度最准的单指标，比裸码率有用得多。

VDF 的做法是**逐级淘汰 + 每级近似平局容差**（其 `QualityRanker`），值得借鉴。

## 2.2 实现要点

**判据列表（按优先级，高者胜）**：

| 顺序 | 判据 | 方向 | 近似平局容差 |
|---|---|---|---|
| 1 | 时长 | 长胜 | 1 秒或 1% |
| 2 | 分辨率（宽×高） | 大胜 | 3% |
| 3 | 每像素位数 | 大胜 | 5% |
| 4 | 码率 | 高胜 | 5% |
| 5 | 帧率 | 高胜 | 0.5 |
| 6 | 文件大小 | 大胜 | 无（精确比较） |

**算法（逐级淘汰，只在平局者之间继续）**：

```
候选集 = 全组
for 判据 in 判据列表:
    若 候选集 只剩 1 个: 结束
    赢家 = 按该判据在候选集中取最优
    平局者 = 候选集中所有"与赢家在该判据上近似相等"的
    若 平局者只有 1 个: 返回 (赢家, 该判据)     # 有唯一赢家，结束
    候选集 = 平局者                             # 否则进入下一级
返回 (当前最优, None)                            # 所有判据都打平
```

**两个关键设计**：
- **只在平局者之间逐级淘汰**，不做加权求和。加权求和会出现"某一项数值巨大就压制其他所有项"的陷阱。
- **返回"由哪个判据决定"**（`decided_by`），用于 UI 展示理由（例如组标题显示「建议保留 xxx.mp4：时长更长」），让用户能判断这个建议是否合理，而不是盲信一个黑盒排序。

**容差为什么必要**（这是本项的精髓）：时长按秒/毫秒计、码率按 kbps 计，这类近似连续的数值几乎永远不相等。没有容差时，一个**只长 200 毫秒**的视频就能压过**分辨率高一倍**的视频。容差让"实际上差不多"的值进入下一级比较。

## 2.3 改动清单

| 位置 | 改动 |
|---|---|
| 新增 | `quality_criteria` 判据定义（含 accessor、方向、容差） |
| 新增 | `pick_keeper(items) -> (keeper, decided_by)` 逐级淘汰实现 |
| 替换 | `_group_quality_key()` 的所有调用点（GUI 的 `best_of`、`group_videos()` 里的组内排序、`render()`、`select_worse_in_groups()`） |
| GUI | 组标题/提示显示 `decided_by` 理由 |
| 新增字段 | `VideoItem.bits_per_pixel`（计算属性：`bitrate / (w*h*fps)`） |
| 可选 | 判据顺序做成用户可调（设置项存 `config.json`） |

> 注意：`group_videos()` 内部也有一份重复的质量排序逻辑，替换时要**一起改**，否则命令行与 GUI 的建议保留项会不一致。

## 2.4 验收标准

1. **分辨率不碾压质量**：构造 A=1080p/200kbps、B=720p/8Mbps，期望保留 **B**（每像素位数远高于 A）。
2. **时长不被忽略**：构造 A=1080p 但只有 30 秒（完整片的一个片段）、B=1080p 完整 30 分钟，期望保留 **B**。
3. **近似平局正确级联**：构造两个时长只差 200 毫秒、但分辨率差一倍的样本，期望按**分辨率**决胜而非时长。
4. **理由可解释**：返回的 `decided_by` 与实际决胜判据一致（单元测试逐例断言）。
5. **一致性**：GUI 的"建议保留"与命令行 `--scan` 输出的 ★ 标记必须指向同一个文件。
6. **回归**：现有 27 项 GUI 测试全通过。

# 任务 3：组代表互验（防止连环并组）

## 3.1 背景与要解决的问题

当前分组用的是**纯并查集**：

```python
for p in range(len(cand)):
    for q in range(p + 1, len(cand)):
        ...
        d = hash_distance(items[i].hashes, items[j].hashes)
        if d <= max_dist:
            union(i, j)      # ← 直接合并，没有任何校验
```

并查集有传递性：只要 `d(A,B) ≤ 阈值` 且 `d(B,C) ≤ 阈值`，就把 A、B、C 并成一组，**哪怕 A 和 C 毫无关系**。

典型受害场景：同一个博主的系列视频、同一部剧的不同集、同一游戏的连续录屏——画面风格、片头片尾、拍摄环境都相似，B 成了 A 和 C 之间的"桥梁"，**整个目录被并成一个巨大的"重复组"**。用户面对一个几十个文件的"重复组"根本无法判断，功能事实上失效。

VDF 在合并两个已有分组之前，会**先验证两组的代表文件互相相似**。这是本项要借鉴的核心。

## 3.2 实现要点

在 `union(i, j)` 之前加一道校验：

```
若 find(i) == find(j): 跳过（已同组）

组I = find(i)，组J = find(j)
代表I = 组I 中质量最高的文件
代表J = 组J 中质量最高的文件

若 i == 代表I 且 j == 代表J:
    直接合并（两者本就互为代表，无需额外校验）

若 hash_distance(代表I, 代表J) ≤ 阈值:
    合并
否则:
    不合并（记录一对"被拒绝的合并"，可用于调试/日志）
```

**要点**：
- 代表取**质量最高的文件**（复用任务 2 的 `pick_keeper`），与 UI 上标 ★ 的"建议保留项"保持一致，用户能理解。
- 校验用**同一套距离函数**（含掩码通道），保证判定口径统一。
- 代价：每次真正合并前多算一次 `hash_distance`。合并次数远少于比较次数（比较是 O(n²) 级别，合并最多 n-1 次），**开销可忽略**。

## 3.3 权衡说明

这道校验会**牺牲一点传递性**：原本 A~B、B~C 就让 A~C 同组，现在可能分成 {A,B} 和 {B,C} 两组（B 出现在两组里不太合适）。

有两种处理方式，需要二选一并写进代码注释：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 拒绝合并**（推荐先做） | 代表不相似就不合并，A、B、C 中 B 会留在先合并的那组 | 实现简单、结果保守 | 可能出现"B 在两组的边缘"这种不完美结果 |
| B. 组内重校验 | 合并后重跑一遍组内两两校验，剔除离群者 | 结果更干净 | 实现复杂、需要处理"剔除后再分组"的循环 |

**先做方案 A**，观察真实数据上的效果再决定是否需要 B。

## 3.4 验收标准

1. **连环场景不再并组**：构造 A、C 为完全不同的视频，B 为"与 A、C 都在阈值内"的过渡样本，期望**不出现**包含 A、B、C 三者的单一分组。
2. **正常场景不受损**：原有 5 个同源样本（原始/改名/转码/裁切/水印）仍必须归为一组——这条是防止"校验过严导致该并的没并"。
3. **性能不退化**：在 500 个文件、含多个大重复组的目录上，分组耗时相对现在**增幅 < 10%**。
4. **可观测**：被拒绝的合并记入 debug 日志（含两个代表的路径与距离），便于排查"为什么没并组"。

## 3.5 风险

- 阈值偏高时校验会过于严格，导致该合并的没合并 → 靠验收标准 2 兜底，并按需引入方案 B。

# 任务 4：零依赖 / 免安装分发

## 4.1 先澄清事实（已实测，2026-10-04）

**本工具运行期不需要 ffmpeg。** 实测依据：

| 验证项 | 方法 | 结果 |
|---|---|---|

## 4.4 方案 C：如果将来真要内置 ffmpeg → 许可证约束

**结论先行：不要内置打包 ffmpeg.exe。** 如果确实要做，必须先理解这些约束：

1. **FFmpeg 的许可证取决于构建方式**：默认是 **LGPL v2.1+**；一旦用 `--enable-gpl`（启用 libx264 / libx265 / libxvid 等 GPL 组件），**整个 FFmpeg 变为 GPL**。
   本机 `C:\ffmpeg\bin\ffmpeg.exe` 实测就是 **GPL 构建**（`-version` 显示 `enable-gpl`、`enable-libx264`，`-L` 输出 GPLv3 声明）。网上流传的多数据编译版（gyan.dev 等）都是 GPL 构建。

2. **用进程调用（`subprocess` 调独立 exe）不构成衍生作品**，属于"聚合"，**我们的 MIT 许可不需要改**。只有静态/动态**链接** FFmpeg 库才会触发传染性。

3. **但分发 ffmpeg.exe 本身仍需合规**：需随包附上对应许可证全文、提供该构建对应源码的获取方式、不得重命名其 DLL、在"关于"里声明使用了 FFmpeg。这会让发布流程变复杂。

4. **⚠️ 陷阱：PyAV 不是"免费午餐"**。
   实测 `av-19.0.1-cp312-abi3-win_amd64.whl`（28 MB，`abi3` 所以 Python 3.14 也能装）的包内**确实带有 `libx264-165.dll` 和 `libx265.dll`**——即它自带的 FFmpeg 也是 **GPL 构建**。想用它来规避 ffmpeg.exe 的许可证问题是行不通的，采用前必须按 GPL 处理（或自行改用 LGPL 构建的 FFmpeg 重新编译，成本很高）。

**因此**：要做音频比对时，优先方案是**让用户按需自行安装 ffmpeg**（用户自己装的软件不受我们的分发义务影响），并在文档里给出一行安装指引；而不是由我们打包分发。

# 任务 5：抽帧后端选型与性能优化

> 起因：讨论中提出「OpenCV 和 ffmpeg 都能抽帧，性能差多少、怎么选」。以下全部为**本机实测**，测试条件见附录 C。

## 5.1 实测数据（1080p H.264 / 60 秒 / 1500 帧，取 12 个采样帧）

| 方法 | 耗时 | 相对最快 | 帧位置准确 | 说明 |
|---|---|---|---|---|
| **OpenCV `grab()`+`retrieve()` 顺序扫** | **1235 ms** | 1.00× | ✅ 精确 | 解码全部帧但不做色彩转换，只在目标处 retrieve |
| **OpenCV `set(POS_FRAMES)`+`read()`（当前做法）** | 1366 ms | 1.11× | ✅ 精确 | 逐位置定位 |
| ffmpeg 单进程（`fps` 滤镜一次产 12 帧，输出 32×32 灰度） | 1692 ms | 1.37× | ✅ 12 帧（已验证字节数） | 需系统装有 ffmpeg |
| OpenCV seek + 再缩放到 32×32 | 2389 ms | 1.93× | ✅ 精确 | 缩放本身约占 785 ms |
| PyAV 单次打开 + `seek` + **解码推进到目标时刻** | 5871 ms | 4.75× | ✅ 精确 | Python 层逐帧推进开销大 |
| ffmpeg 12 个进程（每位置一个，32×32 灰度） | 5681~7643 ms | 4.6~6.2× | ✅ | 进程启动开销是主因 |
| OpenCV 顺序 `read()` 全解码 | 11142 ms | 9.02× | ✅ 精确 | 每帧都做色彩转换，最慢 |

（720p/30 秒样本上的相对关系一致：grab 最快，PyAV 精确 seek 慢 9.05×，ffmpeg 12 进程慢 30×。）

## 5.2 一个必须记录的"测试陷阱"

初测时 PyAV 显示只用了 **179 ms**，比 OpenCV 快 **9 倍**，看起来是明显的赢家。**但那是错的**：那只用了 `container.seek(backward=True)` 后取第一帧，拿到的是**上一个关键帧附近的帧，不是目标位置**。

逐帧核对误差（请求帧号 vs 实际拿到）：

| 请求帧号 | PyAV 只取首帧的实际时刻 | 误差 |
|---|---|---|
| 62 | 0.000 s | **−62 帧（−2.5 秒）** |
| 187 | 0.000 s | **−187 帧（−7.5 秒）** |
| 1437 | 49.760 s | **−193 帧（−7.7 秒）** |

误差最大接近 **8.7 秒**，且会反复取到同一批关键帧。改成"解码推进到目标时刻"后准确了，但速度优势完全消失（反而慢 4.75~9 倍）。

**教训**：性能对比必须同时校验**输出正确性**。只比时间会得出完全相反的结论。（同理，初测里 ffmpeg 单进程方案显示"只拿到 1 帧"也是测试脚本的计数假象——按字节数核对后确认它确实输出了完整的 12 帧。）

## 5.3 结论与建议

1. **保持 OpenCV 作为主抽帧后端。** 现有的 `cv2` 方案在"精确 + 速度"两个维度上都是最优或接近最优；换成 ffmpeg CLI 会慢 4.6~6.2 倍，换成 PyAV 会慢 4.75~9 倍。
   > 这也说明 VDF 的 CLI-per-position 路径本身并不快——它真正的加速来自**进程内原生 FFmpeg 绑定**（复用同一 decoder 与 swscale context），那是 Python 难以复刻的。
2. **加一个自适应后端切换（1.1~2.1× 提速，零新依赖）**：
   ```
   估算两种策略的成本：
     seek 成本 ≈ 采样帧数 × 每次定位成本
     scan 成本 ≈ 总帧数 × 每帧 grab 成本
   取更小者。实测常量（1080p）：
     每次 seek ≈ 114 ms/样本；每帧 grab ≈ 0.82 ms
     → 交叉点 ≈ 1500 帧 ≈ 60 秒（25fps）
   规则：视频 ≲ 1 分钟 → 顺序 grab；更长 → 逐位置 seek
   （常量按像素数缩放；实测标定后写进代码注释）
   ```
   这也让现有的"顺序扫读兜底"从**异常兜底**升级为**正常路径之一**。
3. **不引入 PyAV。** 为抽帧引入 28 MB 依赖却更慢，不划算。**唯一**值得引入的场景是将来做音频比对（它是唯一能在进程内解音频的纯 pip 方案），且届时要处理 4.4 的许可证问题。
4. **ffmpeg 单进程方案可作为"检测到 ffmpeg 时的备选路径"**：它一次进程就把 12 帧直接输出成 32×32 灰度（省掉约 785 ms 的缩放），比"OpenCV seek + 缩放"（2389 ms）快 1.4×。但因为需要用户装有 ffmpeg，只能作为可选加速，不能作为默认。

## 5.4 验收标准

1. 在一批混合时长的视频（10 秒 / 1 分钟 / 30 分钟 / 2 小时）上，自适应切换后的总扫描耗时**不劣于**当前实现，且短于 1 分钟的视频上有明显提速。
2. 切换后取到的采样帧必须**与逐位置 seek 的结果完全一致**（同一批帧号，哈希相同）——用断言保证，不允许为了速度牺牲位置准确性。
3. 对容器不支持帧号定位的文件（如部分 MPEG-TS/AVI），仍能通过顺序扫读拿到帧（现有兜底逻辑不能被破坏）。

# 附录 A：本次分析中已确认的 2 个 Bug

### B1：编码名显示为数字（如「7」「2」）— 已确认，待修

**现象**：扫描多编码样本时，输出里出现

```
11_mpeg2.ts   320x240  0:02  1.21 Mbps  2      417 KB
10_h264.flv   320x240  0:02  265 kbps   7       68 KB
```

编码列显示 `2`、`7`，而不是 `MPEG-2`、`H.264`。

**根因**：`probe_media()` 里取编码时**优先用了 `codec_id`**：

```python
codec = getattr(t, "codec_id", None) or getattr(t, "format", "") or ""
```

而 MediaInfo 的 `codec_id` 是**容器相关的标识**，某些容器里是数字：FLV 里 H.264 的 `codec_id` 是 `"7"`，MPEG-TS 里 MPEG-2 的 `codec_id` 是 `"2"`（已实测确认）。同一段 H.264 在 MP4 里 `codec_id` 是 `"avc1"`（能正常映射成 H.264），在 FLV 里就变成 `"7"`。

**修法**：改为**优先 `format`、退回 `codec_id`**：

```python
raw = getattr(t, "format", None) or getattr(t, "codec_id", "") or ""
```

实测 `format` 字段更可靠（`AVC` → H.264、`MPEG Video` → 需要映射成 MPEG-2），并补充 `norm_codec` 的别名表：`mpeg video` → `MPEG-2`、`avc` → `H.264`。

**验收**：12 个多编码样本的编码列全部显示为人类可读名称，无纯数字。

### B2：GBK 控制台下 exe 崩溃 — 已确认并在真实 cmd 下复现，待修

**现象**：在中文 Windows（代码页 936）的 `cmd.exe` 里运行打包后的 exe，退出码 1：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2713' in position 8: illegal multibyte sequence
```

崩在 `selftest()` 打印 `✓`（`video_dedup.py:2319`）的那一行。

**复现命令**（已实测）：

```bat
chcp 936
build_test\dist\viddedup_probe.exe --selftest
```

**根因**：GBK 能编码汉字，但**不能编码 `✓`(U+2713)、`✗`(U+2717)、`⚠` 等符号**。在 UTF-8 终端（如 Git Bash）下不报错，所以开发时不易发现；一旦用户用 cmd 双击运行就必崩。

**修法**（三处一起做）：

1. **启动时统一 stdout/stderr 编码**，并允许丢弃无法编码的字符而不是崩溃：
   ```python
   for stream in (sys.stdout, sys.stderr):
       if stream is not None:
           try: stream.reconfigure(encoding="utf-8", errors="replace")
           except Exception: pass
   ```
2. **不要把 `✓/✗/★/⚠` 输出到控制台**：改为 ASCII 等价物（`OK` / `FAIL` / `*` / `!`）。GUI 里可以继续用符号（Tk 自己处理编码），但控制台输出必须 ASCII 安全。
3. **`--noconsole` 打包时 `sys.stdout` 为 `None`**，任何 `print()` 都会抛异常 → 统一走一个安全输出函数：
   ```python
   def say(*a):
       s = " ".join(str(x) for x in a)
       try:
           if sys.stdout is not None:
               print(s)
       except Exception:
           pass
   ```

**验收**：在 `chcp 936` 的 cmd 下运行 exe 的 `--selftest` 与 `--scan`，退出码 0，无乱码、无异常。
