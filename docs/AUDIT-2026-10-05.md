## 二、问题清单

### P1 —— 正确性 / 一致性（建议发版前必修）

#### A1. CLI 结果不可复现：同一命令、同一目录，"建议保留"会在两个文件之间跳变

**证据**（本轮实测，同一命令连续跑三次，`--scan` 同一目录）：

```
第 1 次:  建议保留：原始视频.mp4（文件更完整）
第 2 次:  建议保留：同一视频-改个名字.mp4（文件更完整）
第 3 次:  建议保留：原始视频.mp4（文件更完整）
```

同一次运行中，整组顺序也随之变化（谁排第一就是谁）。

**根因**：
1. `run_cli()` 用 `as_completed()` 收集结果（`video_dedup.py:2922`），`items` 列表顺序 =
   **线程完成顺序 → 每次不同**；
2. `pick_keeper()` 最后一级判据「文件大小」的 `tie=None`，直接
   `max(cands, key=size)`（`:1064`）——两个文件**字节完全相同**（各 3,782,720 字节）时，
   `max` 返回**先遇到的那个**，于是随输入顺序漂移。

**影响**：
- "★ 建议保留"是用户决定删哪个文件的依据，结果不可复现会直接损害信任；
- GUI 侧恰好是确定性的（`_scan_worker` 按 `files` 顺序建 `items`），所以
  **GUI 与 CLI 在平局时可能给出不同的保留项**，违反 ROADMAP 任务 2 验收标准 5
  （"GUI 的 ★ 与命令行输出必须指向同一个文件"）。

**建议**：
- CLI 收尾时按路径排序重建 `items`（`items.sort(key=lambda v: v.path.lower())`）；
- `pick_keeper()` 的末级平局改为确定性 tiebreak（例如按 `path` 字典序），保证
  "同输入 → 同输出"，并顺带消除 GUI/CLI 分歧。

### P2 —— 功能与文档不符 / 可用性

#### B1. 「重新分组」不读灰度通道参数，导致两个控件"调了没用"

`regroup_now()`（`video_dedup.py:2830`）只传了 4 个参数：

```python
groups, singles, gsim = group_videos(items, sim_thr, tol_ratio, tol_sec)
```

而 `group_videos` 的签名里 `gray_thr` / `use_gray` / `ignore_black` / `ignore_white`
都有默认值 → **"重新分组"永远用默认的 0.92 + 掩码开启**，完全忽略界面上的
「灰度通道阈值」滑杆与「忽略黑/白像素」复选框。`_on_gray_toggle()`（`:1675`）
也只调用 `render()`，并不会重新分组。

**与文档冲突**：README §3 明确写"调完阈值点 **重新分组** 即可，无需重新扫描"，
以及"界面上的「忽略黑/白像素」开关可以关掉掩码通道做对照"。
按当前实现，**这两个控件只有在"开始扫描"时才生效**，"重新分组"和
回收站/备份后的自动重分组（`action_trash` / `action_backup` 都调用
`regroup_now(silent=True)`）一律用默认值 —— 用户看到的会是"改了参数没反应"。

**建议**：`regroup_now()` 读取 `self.gray_thr_var` / `self.ignore_bw_var` 一并传入；
`_on_gray_toggle()` 改为触发一次重分组（或明确提示"需重新分组"）。

#### B2. 消息框一律未设 parent（18 处），会造成"界面假死"的错觉 —— 本次事故的直接成因

全文件 18 处 `tkmsg.showinfo/showwarning/showerror/askyesno` **没有一处传 `parent=`**。
其中最危险的是 `_poll_queue()` 里的错误分支（`:2181`）：它由 `root.after` 驱动，
一旦弹出模态框就进入**嵌套模态循环**；在没有父窗口约束、窗口未置顶的窗口环境下，
对话框可能落在主窗口之后甚至不可见，此时主界面既不响应也无法关闭 —— **用户完全无法
区分"在等待"和"已死机"**。

**已实际发生**：本轮审计中，`tools/gui_smoketest.py`（内部 `root.withdraw()` 隐藏主窗口）
运行后，审计机桌面卡死、无法打开新应用，等待 5 分钟无进展。这与上述机制完全吻合。

**建议**：统一封装一个 `_dialog(fn, msg, **kw)` 传 `parent=self.root`；
或给所有调用点补 `parent=self.root`。同时建议 `gui_smoketest.py` 增加超时保护
（当前 `wait_scan` 虽然写了 `timeout`，但模态框会卡住 `root.update()` 本身，
超时逻辑无法生效）。

#### B3. 掩码通道的实际增益被文档高估（结论口径与实测不符）

本轮用**函数级探针**直接对比"掩码开 / 掩码关"（同一批采样帧）：

| 对比 | 掩码开 | 掩码关 | 差异 |
|---|---|---|---|
| 原片 vs **半透明水印**样本（`带水印版本.mkv`） | 98.95% | **99.04%** | 掩码反而**略降** 0.09pp |
| 原片 vs 完全无关视频 | **74.93%** | 66.12% | 掩码把异源相似度**抬高 8.8pp**（压缩安全区） |

而 `--selftest` 里的掩码校验用的是**完全不透明白块**
（`cv2.rectangle(fr, ..., (255,255,255), -1)`，纯白 255）：95.16% → 99.96%，
差异巨大、结论非常乐观。

原因很清楚：`tools/make_testdata.py` 造的"真实"水印是
`fontcolor=white@0.85 : box=1 : boxcolor=black@0.45`
（**半透明白字 + 半透明黑底**）。合成到画面后，这些像素**既不到 240 也不低于 32**，
于是既不落入"近白"也不落入"近黑"，**掩码根本没有排除到它们** —— 掩码在这个样本上
几乎不起作用；真正把水印副本认出来的是 **32×32 灰度图的逐像素绝对差（SAD）本身**。

**影响**：README §3 与 Release 说明都把"抗水印"归功于「灰度掩码通道」，
这在**半透明水印**这一最常见场景下是不成立的。掩码的真实适用面是
近黑/近白干扰（黑边、纯白台标、烧制白字幕），且它的代价是把异源相似度也抬高。

**建议**：
1. 在 `--selftest` 里**同时**加入"半透明水印"用例（当前只测纯白块），
   否则自检会持续给出乐观假象；
2. 修正 README / Release 说明的口径：把"抗水印"的功劳归给**灰度 SAD 通道**，
   把"掩码"的定位改回它真正的用途（黑边 / 近黑白干扰），并说明对半透明水印无效。

#### B4. 配置项"存了不读"：4 个参数每次启动被重置

`_save_cfg()`（`:1692`）写入 `tol_ratio`、`tol_sec`、`sample`、`min_size`、`backup_dir`，
但 `_cfg()` 只在 6 个键上被调用（`last_folder` / `thumb_mode` / `view_mode` /
`threshold` / `gray_threshold` / `ignore_bw`）。因此用户调过的
**时长容差、采样帧数、跳过小于(MB)、上次备份目录**在重启后会静默回到默认值。

**建议**：`__init__` 里为这 4 个变量补 `_cfg(...)` 读取（并做类型兜底）。

## 三、值得肯定之处（避免只列问题）

- **降级设计扎实**：opencv / pillow / imagehash / pymediainfo / send2trash 逐个可选，
  缺任一个都能降级运行；`--noconsole` 下 `sys.stdout is None` 也有 `_NullWriter` 兜底、
  还有 `_crash_report()` 写崩溃日志，这是踩过坑之后的成熟处理。
- **安全边界清楚**：没有任何不可逆删除路径 —— 回收站失败会降级为"移动到同目录
  `_视频查重回收站`"，且判据用"源文件是否还存在"而不是返回值（这一点很专业）。
- **隐私声明可核验**，不是口号：主程序零网络导入。
- **工程闭环完整**：自检、样本生成器、GUI 回归、性能基准（含"必须同时校验取帧正确性"
  这一教训）齐备；发布走脚本 + SHA256 + GitHub Release，本轮独立复核字节一致。
- **文档质量高于同类小工具**：ROADMAP 记录了"照抄 VDF 判据顺序会出错"
  "掩码有效像素下限 6.25% 造成严重误判"等真实踩坑，对后来者价值很高。
- 批处理为 CRLF、`.gitattributes`/`.gitignore` 配置合理、工作区干净。
